## Problem Statement

Fund managers run their investment process across 6+ disconnected tools: Bloomberg for data, Excel for valuation models, shared folders for memos, Slack for IC discussions, spreadsheets for portfolio tracking, and various screeners for idea generation. This fragmentation causes institutional memory to leak. Analysts forget about researched names. Thesis files go stale. The screener rediscovers things that were already deep-dived. Nobody updates the spreadsheet. The investment process, which should be a tight feedback loop, becomes a collection of dead files in a shared drive.

FundOps solves this by making the AI agents BE the workflow, not tools bolted onto a human workflow. Scout doesn't help you screen — Scout IS the screener. Val doesn't help you write a thesis — Val IS the analyst. The pipeline runs continuously and nothing falls through the cracks. The human (PM) intervenes at decision points, not at every step.

## What Makes This Cool

The core insight: **most fintech AI is "AI-augmented human workflow." FundOps is "human-augmented AI workflow."** The agents drive the process continuously. The PM reads the output, makes the calls, and the system learns from outcomes.

The self-improving loop is the killer feature. After 6 months, your Scout gets better at finding YOUR kind of winners because it tracked which screens led to buys, which buys made money, and which thesis assumptions actually held. The agents develop institutional memory that never quits, never forgets, and never takes a sick day.

## Constraints

- Must be pluggable: any data provider (FMP, Bloomberg, FactSet, SEC EDGAR, custom APIs)
- Must keep the human in the loop at every decision point (no autonomous trading)
- Must work for a solo/small fund PM (1-3 person team) as the primary user
- Python-based backend (existing agent codebase is Python)
- Real interactive web dashboard (not static HTML)
- Self-improving requires outcome tracking (trade data flowing back to agents)
- Must handle sensitive financial data securely

## Premises

1. **The workflow IS the product.** The value is the pipeline (Scout -> Val -> Judge -> Memo -> Ledger -> Pulse -> Vanguard) and the fact that nothing falls through the cracks. A fund manager's process is their edge, and this system encodes it.

2. **Pluggable data beats owned data.** Don't try to be Bloomberg. Let users bring their own data providers. The platform orchestrates, it doesn't collect.

3. **Self-improving agents require outcome tracking.** For agents to get better, trade-level outcome data must flow back. What did Scout surface -> what did the PM buy -> what happened?

4. **A real web app dashboard is table stakes.** Static HTML won't work for anyone else. Needs auth, real-time data, and actionable UI.

## Approaches Considered

### Approach A: "The Next.js Dashboard" — Minimal Viable
Wrap existing Python agents in a real Next.js web app with REST API. Ships fast but hardcoded to current data sources and no learning loop.
- Effort: M (human: ~2 weeks / CC: ~2-3 days)
- Risk: Low
- Completeness: 4/10

### Approach B: "The Agent Framework" — Ideal Architecture
Build a pluggable agent framework where each agent is a config-driven module. Data connectors are plugins. Workflow is a DAG. Feedback loop tracks outcomes.
- Effort: L (human: ~2 months / CC: ~1-2 weeks)
- Risk: Medium
- Completeness: 8/10

### Approach C: "The CLI-First Platform" — Creative/Lateral
CLI-first platform (pip install fundops). YAML config for agents, terminal-native. Fast to distribute but limits audience.
- Effort: M (human: ~3 weeks / CC: ~4-5 days)
- Risk: Medium
- Completeness: 6/10

## Recommended Approach

**Approach B: The Agent Framework.** This is the version that actually solves the fragmentation problem. A and C are just "your setup, slightly more polished." B is the actual product.

### Key Components

**1. Agent Registry & Plugin System**
Each agent (Scout, Val, Judge, etc.) is a plugin with a standard interface:
```python
class AgentPlugin:
    name: str
    inputs: list[str]       # what data it needs
    outputs: list[str]      # what it produces
    config: dict            # user-configurable params (hurdles, models, etc.)

    async def run(self, context: PipelineContext) -> AgentResult
    async def learn(self, outcome: OutcomeRecord) -> None  # feedback loop
```

**2. Data Connector Layer**
Standard interface for data providers:
```python
class DataConnector:
    name: str
    capabilities: list[str]  # ["quotes", "financials", "filings", "estimates"]

    async def get_quotes(self, tickers: list[str]) -> dict
    async def get_financials(self, ticker: str, years: int) -> dict
    async def get_filings(self, ticker: str, filing_type: str) -> dict
```
Ship with FMP + SEC EDGAR connectors. Bloomberg/FactSet are future plugins.

**3. Workflow DAG Engine**
The pipeline is defined as a DAG in YAML:
```yaml
workflow:
  name: "Thomas's Value Pipeline"
  agents:
    - scout:
        schedule: "weekly"
        hurdle: 15
        lenses: [dislocation, compounder]
    - val:
        trigger: "scout.handoff"
        model: "gpt-5-mini"
        web_search: true
    - judge:
        trigger: "val.complete"
        hurdle_base: 20
        hurdle_bear: 15
        ai_review: true
    - memo:
        trigger: "judge.pass"
        cost_limit: "$5/week"
    - pulse:
        schedule: "daily"
        held_only: true
    - vanguard:
        trigger: "pulse.alert OR manual"
```

**4. Feedback & Learning Loop**
```
Scout surfaces CALM ──> PM buys at $75 ──> 6 months later: $95 (+27%)
                                            │
                                            ▼
                              Feedback DB records:
                              - Scout found it via dislocation lens
                              - Val's DCF was $110 (close to actual)
                              - Judge's bear case was $65 (never hit)
                              - Key assumption "egg prices stable" held
                                            │
                                            ▼
                              Scout learns: dislocation lens + food sector
                              + high FCF yield = strong signal for this PM

                              Judge learns: this PM's bear cases in food
                              sector tend to be conservative (good)
```

**5. Dashboard (Next.js)**
- Per-agent tabs with real-time data
- Interactive: click ticker to see full pipeline history
- Action buttons: "Run Val on this", "Override Judge decision", "Add to portfolio"
- Configurable: each PM arranges their dashboard
- Mobile-responsive for checking portfolio on the go

## Plugin Mechanism

Plugins are discovered via Python entry_points (setuptools). Each agent is a Python package that registers itself:

```toml
# pyproject.toml for a custom agent
[project.entry-points."fundops.agents"]
my_scout = "my_package.scout:MyScoutAgent"
```

At startup, the orchestrator scans `fundops.agents` entry_points and loads them into the registry. Built-in agents (Scout, Val, Judge, etc.) are registered the same way.

Data connectors use the same mechanism via `fundops.connectors` entry_points.

## DAG Execution Model

The workflow engine is a **simple state machine**, not a full DAG executor like Airflow. Each agent has:
- A trigger condition (schedule, upstream completion, or manual)
- Input requirements (what data it reads)
- Output artifacts (what it writes)

The state machine processes events sequentially. When Scout completes, it emits a "scout.complete" event. Val agents listening for "scout.handoff" pick up the candidates. There is no parallel scheduling in v1 ... agents run one at a time via asyncio. This is sufficient for a single-user system processing 15-20 tickers.

## Error Handling & Retries

- **FMP API failures:** 3 retries with exponential backoff (1s, 4s, 16s). If all fail, skip the ticker and log the error. Scout continues with remaining tickers.
- **LLM timeouts (GPT-5 mini):** 2 retries with 60s timeout each. On failure, Val/Judge records a "FAILED" status for the ticker. User can retry manually from dashboard.
- **Partial runs:** Each agent writes a status file (.status.json) with progress. If interrupted, the next run picks up from the last completed ticker.
- **Data connector failures:** Connector returns a standard error object. Agent decides whether to proceed with partial data or skip.

## Feedback Loop: Recording vs Learning

The feedback loop has two distinct phases:

**Phase A: Outcome Recording (v1, buildable)**
- Manual trade entry: ticker, shares, cost basis, date
- Automatic performance tracking: return vs SPY, thesis assumption monitoring
- Scorecard per agent: "Scout surfaced this, Val said BUY, Judge said PASS, PM bought"
- Dashboard shows: hit rate by lens, by sector, by agent

This is a database + dashboard feature. No ML, no statistics, no research problems.

**Phase B: Automated Learning (v2+, research)**
- Scout: adjust lens weights based on hit rate by sector/style
- Val: calibrate confidence scores based on thesis accuracy
- Judge: update hurdle thresholds based on false positive/negative rates
- This requires 6+ months of outcome data and is genuinely hard

v1 ships outcome recording. The data accumulates. v2 builds learning on top of real data.

## Secrets & API Key Management

- API keys stored in `.env` file (gitignored), loaded at startup
- Data connector config in YAML references env var names, not values:
  ```yaml
  connectors:
    fmp:
      api_key: "${FMP_API_KEY}"
    openai:
      api_key: "${OPENAI_API_KEY}"
  ```
- No secrets in config files, no secrets in the database
