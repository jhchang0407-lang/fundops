## Problem Statement

FundOps has 8 independent learning mechanisms scattered across 4 agent docs: Library autopsies, bias detection, screener feedback, thesis health decay, memo profile refinement, allocator recompilation, outcome tracking, and strategy conversation refinement. None of these are connected. The Library doesn't know about screener feedback. The screener doesn't know about outcome tracking. The bias detector can't access thesis health decay data. Every agent learns in isolation.

The result: the system doesn't actually get smarter. It accumulates data in separate silos. The user has to manually connect "we kept overestimating margin expansion" with "the IC should apply bigger haircuts to margin assumptions." That's the job of a system, not a person.

## What Makes This Cool

FundOps is the first open-source investment tool with a unified learning loop that genuinely improves over time. Not just "we track performance" (every tool does that). The system:

1. Learns at three speeds simultaneously (fast user feedback, medium outcome tracking, slow bias correction)
2. Tracks a shadow portfolio of everything you DIDN'T buy to measure whether your filters are right
3. Earns autonomy over time. It starts by asking permission for every adjustment. After proving its suggestions would have been correct N times, it graduates to auto-adjusting with notification. Trust is earned, not configured.
4. Shows you everything it learned in a transparent, auditable Learning Log. No black boxes.

## Constraints

- **Not a new agent.** Self-improvement is cross-cutting infrastructure that every agent reads from and writes to. It lives in `backend/learning/` + the Library.
- **Data-dependent.** Fast loop works immediately. Medium loop needs 3+ months. Slow loop needs 200+ resolved outcomes. The system is honest about what's active and what's accumulating.
- **Autonomy is opt-in.** Default mode is suggest-and-confirm. User must explicitly enable autopilot. Manual mode exists for users who want to pull reports.
- **No external ML infrastructure.** SQLite + Python. No MLflow, no vector DBs for this layer (Library already handles embeddings). Simple queries and heuristics, not neural nets.
- **Cost:** Near-zero for fast/medium loops (just DB writes + queries). Slow loop (bias detection) is ~$2-5/monthly batch (LLM calls for post-mortem analysis).

## Premises

1. Self-improvement is cross-cutting infrastructure, not an agent. Every agent reads from and writes to it.
2. Three learning speeds, all connected. Fast feeds medium, medium feeds slow.
3. Three autonomy modes: autopilot (auto-adjust + notification), suggest-and-confirm (default), manual.
4. Transparency is non-negotiable. Learning Log is visible and auditable in all modes.
5. Connects existing agent learning surfaces rather than adding new ones.
6. System needs data before it can learn. Design must be honest about activation thresholds.

## Recommended Approach

**Approach B: Unified Learning System** with all three speeds, counterfactual tracking, and autonomy graduation.

### Architecture

#### 1. The Learning Log (central store)

Every learning signal in the system flows through one table. This is the unified store that replaces the scattered silos.

```python
class LearningEvent(BaseModel):
    """Every piece of learning signal in the system."""
    id: int
    timestamp: str
    agent: str              # which agent produced this signal
    event_type: str         # see event types below
    ticker: str | None
    speed: str              # "fast" | "medium" | "slow"

    # Signal data (what happened)
    signal: dict            # event-type-specific data
    # Examples:
    #   fast feedback:  {"action": "dismissed", "reason": "value trap", "screener_score": 72}
    #   medium outcome: {"predicted_return": 28, "actual_return": 12, "period_months": 6}
    #   slow bias:      {"bias_type": "margin_expansion", "sector": "retail", "magnitude": -5.2}

    # Resolution (what we did about it)
    resolved: bool = False
    autonomy_action: str | None   # "applied" | "suggested" | "logged"
    user_response: str | None     # "accepted" | "rejected" | "modified" | None
    correction_applied: dict | None  # what changed in which agent's profile
    resolved_at: str | None

# Event types by speed
FAST_EVENTS = [
    "screener_dismiss",       # user dismissed a screener pick
    "screener_promote",       # user promoted a screener pick
    "thesis_feedback",        # user gave feedback on thesis quality
    "memo_refinement",        # user refined memo profile via conversation
    "allocator_override",     # user overrode an allocator recommendation
    "ic_override",            # user overrode IC verdict (bought despite NO_PASS)
]

MEDIUM_EVENTS = [
    "outcome_resolved",        # a thesis has 6+ months of outcome data
    "counterfactual_start",    # a rejected ticker is now being tracked
    "counterfactual_resolved", # a rejected ticker has 6+ months of data
    "thesis_health_update",    # periodic thesis health check result
    "assumption_breach",       # a specific thesis assumption violated
]

SLOW_EVENTS = [
    "bias_detected",          # systematic error pattern found
    "bias_correction_proposed", # correction ready for application
    "autonomy_graduation",    # system earned a higher autonomy level for a correction type
]
```

#### 2. Three Learning Speeds

**FAST LOOP: User Feedback (immediate)**

Every user action that expresses a preference is captured.

```
User dismisses CALM from screener ("value trap, declining industry")
  → learning_events: {agent: "screener", event_type: "screener_dismiss",
     signal: {ticker: "CALM", reason: "value trap", tags: ["declining_industry"]}}

Next screener run:
  → query: last 30 days of dismissals, group by reason
  → if pattern found (3+ dismissals with same tag):
    → SUGGEST: "You've dismissed 4 declining-industry stocks. Add a penalty?"
    → or AUTOPILOT: auto-penalize, log the change
```

Agents that write fast events:
- Screener: dismiss/promote
- IC Review: user overrides verdict
- Memo: user refines profile ("more on capital allocation")
- Allocator: user overrides swap/trim recommendation

Agents that read fast events:
- Screener: incorporates dismiss patterns into next scoring run
- Memo: tracks which refinements the user made most often
- Allocator: adjusts recommendations based on override patterns

**MEDIUM LOOP: Outcome Tracking (weeks to months)**

For every research output, track what actually happened.

```
Thesis on FISV at $57 predicted 28% return over 3 years
  → archived in Library with price_at_memo = $57
  → 6 months later: FISV at $72 → actual_return = 26% (annualized ~52%)
  → learning_events: {event_type: "outcome_resolved",
     signal: {ticker: "FISV", predicted: 28, actual_annualized: 52,
              return_sources_predicted: {discount: 15, growth: 8, margin: 5},
              return_sources_estimated_actual: {discount: 30, growth: 15, margin: 7}}}
```

**Counterfactual Shadow Portfolio:**

For every IC NO_PASS and every user dismissal, track what WOULD have happened.

```
Judge said NO_PASS on AMZN at $185 (bear case return only 8%)
  → learning_events: {event_type: "counterfactual_start",
     signal: {ticker: "AMZN", rejection_price: 185, rejection_agent: "judge",
              rejection_reason: "bear case 8% < 15% hurdle"}}
  → 6 months later: AMZN at $220 → counterfactual_return = 19%
  → learning_events: {event_type: "counterfactual_resolved",
     signal: {ticker: "AMZN", rejection_price: 185, current_price: 220,
              return_pct: 19, rejection_was_correct: false,
              rejection_agent: "judge", rejection_reason: "bear case too conservative"}}
```

**Outcome resolution schedule:**
- Check at T+3 months, T+6 months, T+12 months from research date
- Each check generates a learning event
- Library's autopsy engine runs the detailed post-mortem at T+6 months

Agents that write medium events:
- Library: outcome resolution, counterfactual resolution
- Portfolio Monitor: thesis health updates, assumption breaches

Agents that read medium events:
- Library: autopsy engine uses resolved outcomes
- Screener: "stocks in sector X that we passed on outperformed by Y%"
- IC Review: "our bear cases on SaaS were 15% too conservative"

**SLOW LOOP: Bias Detection + Autonomy Graduation (200+ events)**

Aggregates medium events to find systematic patterns.

```
After 200+ resolved outcomes:
  → BiasDetector queries learning_events where event_type = "outcome_resolved"
  → Groups by: sector, return_source, agent, strategy_type
  → Finds: "We overestimate margin_expansion in consumer_staples by 4.8% on average"
  → learning_events: {event_type: "bias_detected",
     signal: {bias_type: "return_source", category: "margin_expansion",
              sector: "consumer_staples", direction: "overestimate",
              magnitude: 4.8, sample_size: 23, confidence: 0.82}}
```

**Bias correction flow:**

```
SUGGEST mode (default):
  → System surfaces in strategy chat: "I've detected that we consistently
     overestimate margin expansion in consumer staples by ~5%. This is based
     on 23 resolved theses over 14 months. Want me to adjust the IC stress-test
     to apply an extra 5% haircut on margin assumptions for consumer staples?"
  → User: "Yes"
  → learning_events: {event_type: "bias_correction_proposed",
     autonomy_action: "suggested", user_response: "accepted",
     correction_applied: {agent: "ic_review", field: "margin_expansion_haircut",
                          sector: "consumer_staples", adjustment: -5.0}}

AUTOPILOT mode:
  → Same detection, but auto-applies and notifies:
     "Applied: IC Review now applies 5% extra margin haircut on consumer staples
      (based on 23 theses over 14 months). [Undo] [Details]"
```

#### 3. Autonomy Graduation

The system doesn't start in autopilot. It earns it.

```python
class AutonomyLevel(BaseModel):
    """Per-correction-type autonomy level."""
    correction_type: str      # e.g. "screener_dismiss_pattern" or "bias_margin_haircut"
    current_level: str        # "manual" | "suggest" | "autopilot"
    suggest_accuracy: float   # % of suggestions user accepted (rolling 20)
    suggest_count: int        # total suggestions made
    graduated_at: str | None  # when it moved to current level

GRADUATION_THRESHOLDS = {
    "manual_to_suggest": {
        "min_events": 5,        # need 5+ learning events of this type
    },
    "suggest_to_autopilot": {
        "min_suggestions": 20,  # made 20+ suggestions (robust sample)
        "min_acceptance": 0.8,  # user accepted 80%+
    },
}

async def check_graduation(correction_type: str) -> AutonomyLevel:
    """Check if a correction type should graduate to a higher autonomy level."""
    level = db.get_autonomy_level(correction_type)

    if level.current_level == "manual":
        events = db.count_learning_events(correction_type)
        if events >= 5:
            # Enough data to start making suggestions
            return AutonomyLevel(
                correction_type=correction_type,
                current_level="suggest",  # proposed graduation
            )
            # "I have 5+ observations for this pattern. Want me to start
            #  suggesting adjustments instead of just logging them?"

    elif level.current_level == "suggest":
        if (level.suggest_count >= 20 and level.suggest_accuracy >= 0.8):
            # High accuracy over 20+ suggestions = earned trust
            return AutonomyLevel(
                correction_type=correction_type,
                current_level="autopilot",  # proposed graduation
                suggest_accuracy=level.suggest_accuracy,
                suggest_count=level.suggest_count,
            )
            # "I've made 22 suggestions for this type and you accepted 19 (86%).
            #  Want to let me handle this automatically?"

    return level  # no change
```

**Autonomy is per-correction-type, not global.** The system might be in autopilot for "screener dismiss patterns" (high accuracy, lots of data) but still in suggest mode for "IC Review margin haircuts" (newer, less data). The user can also manually override any correction type back to suggest or manual.

#### 6. DB Schema

```sql
-- Central learning event store
CREATE TABLE learning_events (
    id INTEGER PRIMARY KEY,
    timestamp TEXT NOT NULL,
    agent TEXT NOT NULL,
    event_type TEXT NOT NULL,
    ticker TEXT,
    speed TEXT NOT NULL,       -- "fast" | "medium" | "slow"
    signal TEXT NOT NULL,      -- JSON
    resolved BOOLEAN DEFAULT FALSE,
    autonomy_action TEXT,      -- "applied" | "suggested" | "logged"
    user_response TEXT,        -- "accepted" | "rejected" | "modified"
    correction_applied TEXT,   -- JSON: what changed in which agent
    resolved_at TEXT
);
CREATE INDEX idx_learning_speed ON learning_events(speed, event_type);
CREATE INDEX idx_learning_agent ON learning_events(agent, timestamp);
CREATE INDEX idx_learning_ticker ON learning_events(ticker, event_type);

-- Counterfactual shadow portfolio
CREATE TABLE counterfactuals (
    id INTEGER PRIMARY KEY,
    ticker TEXT NOT NULL,
    rejection_date TEXT NOT NULL,
    rejection_price REAL NOT NULL,
    rejection_agent TEXT NOT NULL,  -- "judge" | "user" | "screener"
    rejection_reason TEXT,
    resolved BOOLEAN DEFAULT FALSE,
    checks TEXT,                    -- JSON: [{date, price, return_pct}] at 3mo, 6mo, 12mo
    final_verdict TEXT              -- "correct_rejection" | "missed_opportunity"
);
CREATE INDEX idx_counterfactual_ticker ON counterfactuals(ticker, resolved);

-- Per-correction-type autonomy levels
CREATE TABLE autonomy_levels (
    correction_type TEXT PRIMARY KEY,
    current_level TEXT NOT NULL DEFAULT 'manual',
    suggest_count INTEGER DEFAULT 0,
    suggest_accepted INTEGER DEFAULT 0,
    suggest_accuracy REAL DEFAULT 0,
    graduated_at TEXT,
    user_override TEXT              -- "locked_suggest" | "locked_manual" | NULL
);
```

#### 9. Integration with Existing Designs

This design plugs into the existing 7 agent docs + master design. It does NOT modify any agent's core logic. It adds:

1. **Every agent calls `learning_log.record()` at the end of its run** (same pattern as Library archival)
2. **Every agent calls `learning_log.get_adjustments(agent_name)` at the start of its run** to read applicable corrections
3. **The strategy conversation routes learning-related messages** ("what has the system learned?") to the Learning Dashboard API

The master design's Section 7 (FundOps Architecture Pattern) gains a 4th layer:

```
Layer 1: AI Generates Rules (from strategy)
Layer 2: Deterministic Execution (rules handle math)
Layer 3: AI Narrates and Reasons (for qualitative decisions)
Layer 4: System Learns from Outcomes (self-improvement)  ← NEW
```

#### 10. Error Handling

- **Outcome resolution fails (ticker delisted, data unavailable):** Mark the outcome as `resolution_failed` with reason. Exclude from bias calculations. Don't retry indefinitely... 3 failed checks → mark as `tracking_stopped`.
- **Counterfactual check fails:** Same pattern. Mark as `tracking_stopped` after 3 consecutive failures.
- **Bias detection LLM returns garbage:** Validate structured output. If the BiasProfile has biases with sample_size < 10 or magnitude > 30%, discard as unreliable. Log the failure.
- **Graduation logic edge case:** If a user's acceptance rate drops below 60% after graduating to autopilot, auto-downgrade back to suggest mode with a notification: "Your recent feedback suggests my adjustments for [type] aren't matching your preferences. Switching back to suggest mode."

#### 11. Data Retention

Learning events are kept indefinitely (they're small, ~1KB each). At 100 events/month, that's ~1.2MB/year. Not a concern for SQLite.

Counterfactuals are resolved at 12 months and archived (moved to `counterfactuals_archive`). Active tracking stops after resolution.

Bias profiles are versioned. Old versions are kept for historical comparison but only the latest is active.

#### 12. Migration from Scattered Mechanisms

The existing agent-specific learning surfaces (Library autopsies, screener feedback table, etc.) continue to work as-is. The Learning Log is an ADDITION, not a replacement. Each agent writes to both its own storage AND the Learning Log. Over time, the agent-specific stores become read-only legacy and the Learning Log becomes the single source of truth. No big-bang migration needed.

#### 13. Bias Detection Threshold Clarification

The 200-outcome threshold counts BOTH resolved outcomes (stocks we bought) AND resolved counterfactuals (stocks we rejected). A concentrated portfolio with 14 positions generates ~14 outcomes/year but ~50+ counterfactuals/year (every screener run produces 15+ rejections). With counterfactuals included, the 200-event threshold is reachable in ~3 years of active use, not 10-20.

## Open Questions

1. **Counterfactual resolution timing.** Checking at 3/6/12 months is arbitrary. Should the system check whenever the rejected ticker has a significant price move (>20% in either direction)?
2. **Learning decay.** Should old learning events be weighted less? A dismissal pattern from 2 years ago may not reflect current preferences. Rolling window or exponential decay?
3. **Cross-strategy learning.** If a user changes their strategy, should old learning events be invalidated? The bias patterns may be strategy-specific.

## Success Criteria

- Fast loop: user dismisses 5 screener picks for the same reason → system proposes a scoring adjustment within the next run
- Medium loop: 10+ outcomes resolved → counterfactual scorecard shows rejection accuracy
- Slow loop: 200+ outcomes → bias profile detects at least one systematic error with >80% confidence
- Autonomy graduation: screener feedback loop graduates from suggest to autopilot after 10+ correct suggestions
- Learning Dashboard shows all events in a readable timeline with clear "what changed and why"
- User can lock any correction type to manual at any time
- All learning events are queryable via API for downstream consumption
