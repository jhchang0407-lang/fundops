## Problem Statement

The investment memo agent generates 4 hardcoded sections (Opportunity Brief, Valuation Analysis, Financial Quality, Risks & Bear Case) with a value-investor lens baked into every prompt. A momentum investor gets the same memo structure as a value investor. The `_build_strategy_lens()` method appends strategy text to prompts, but it's cosmetic — the sections, their depth, and their focus areas are identical regardless of strategy.

The deeper problem: FundOps has no unified settings philosophy for how strategy flows into agent behavior. The screener v2 generates scoring code from strategy. The thesis v2 adapts narrative focus. The IC review v2 shapes thresholds. But each does it independently. There's no shared "here's how a user configures what an agent does" pattern.

The investment memo is the right place to nail this pattern because it's the most user-facing output. You READ a memo. You don't read a screener score. If the memo doesn't feel like YOUR memo, nothing else matters.

## What Makes This Cool

Your investment memo adapts to who you are. A value investor's memo spends 40% of its words on valuation and discount analysis with a thin catalyst section. A momentum investor's memo leads with price action and catalyst timeline, with a thin balance sheet section. The defaults come from your strategy conversation. But you keep talking to the AI — "I want more on capital allocation history" — and the memo evolves.

No forms. No sliders. No template picker. The conversation IS the settings page.

And users can add or remove sections entirely. "Add a management quality section." "Remove the financial quality section, the research report covers that." The system checks if the data sources support it and adds it.

## Constraints

- **Data sources:** SEC EDGAR (10-K/10-Q text, financials) + yfinance (price, basic metrics). FMP optional for estimates. Custom sections are constrained by available data — the system must gracefully handle "this section needs data you don't have."
- **Cost:** Investment memo is 4 LLM calls at ~$0.10-0.15 each. Adding sections adds cost linearly. Must stay under $2/memo.
- **Existing code:** `MemoAgent._generate_investment()` in `backend/agents/memo.py` is the current pipeline. 4 hardcoded sections with `_build_strategy_lens()` appended. The research report (`_generate_research()`) and its jinja2 prompts stay unchanged.
- **Strategy conversation:** Already exists as persistent chat UI. Strategy stored in DB with north_star + dimensions. MemoAgent already auto-fetches strategy from DB.
- **Unified pattern:** Whatever we build here should be extractable later into a shared AgentProfile layer for thesis and IC review. Don't build the abstraction now, but don't make choices that prevent it.

## Premises

1. The 4-section backbone (Opportunity Brief, Valuation, Financial Quality, Risks) is a sensible default for most strategies. Strategy changes emphasis, not structure.
2. The strategy conversation is the primary settings interface. Users describe what they want, the AI updates configs. No manual JSON/sliders.
3. Data availability (SEC + yfinance) constrains custom sections. Focus control within sections is the primary lever. Custom sections become richer with richer data sources.
4. This configurability model should be unified across thesis, IC review, and memo eventually. Build it right on memo first.
5. Research report stays as-is. Investment memo is the strategy-aware document.

## Cross-Model Perspective

Claude subagent (independent cold read, no conversation context):

- **Coolest version:** "The memo that rewrites itself after you read it." Instrument the read path — track which sections users expand, skip, act on. After 5-10 memos, the system has a usage-derived attention model. The conversation sets the prior. Usage updates the posterior.
- **Key insight:** The builder's quote "you need to have constant conversation that adds to this" reveals excitement about relationship-based configuration, not template-based. Like a junior analyst learning what their PM cares about over 6 months.
- **Existing 50%:** Instructor (jxnl/instructor) for structured outputs + DSPy for optimizable prompts. The 50% to build: strategy-to-schema compiler, feedback ingestion, unified orchestration.
- **Weekend prototype:** `MemoProfile` dataclass → `strategy_to_profile()` → wire into prompts → conversational `refine_profile()` → `memo_feedback` DB table for future learning.

The feedback instrumentation idea (tracking reads, not just writes) is the right 10x vision. We're not building it now, but the schema should support it.

## Approaches Considered

### Approach A: MemoProfile — Strategy-Driven Section Weights
Add a `MemoProfile` layer between strategy DB and memo prompts. Each section gets a `depth` (1-5) and `focus_directives` list. Strategy conversation generates the default profile. Conversational refinement updates it. Same 4 sections, different depth and focus.
- Effort: M | Risk: Low | Completeness: 8/10
- Pro: Clean, ships fast, validates the pattern
- Con: Can't add/remove sections. Depth=1 feels like "why is this here"

### Approach B: MemoProfile + Section Composition (CHOSEN)
Everything in A, plus users can add/remove/reorder sections through conversation. Section registry defines available sections (data requirements, what it covers). Strategy generates default set. User says "add catalyst timeline" and the AI adds it if data supports it.
- Effort: M-L | Risk: Med | Completeness: 9/10
- Pro: Full flexibility, extensible for future data sources, section registry is reusable
- Con: Custom sections may produce thin output with limited data. Need graceful "this needs data you don't have" handling.

### Approach C: Unified Agent Settings Layer
Everything in B, plus shared `AgentProfile` abstraction across thesis, IC, memo. One conversation updates all agents.
- Effort: L | Risk: Med-High | Completeness: 10/10
- Pro: The dream. Single settings layer for everything.
- Con: Premature abstraction before validating the pattern on one agent.

## Recommended Approach

**Approach B: MemoProfile + Section Composition.**

Build the MemoProfile as a standalone pattern on the investment memo. Prove it works. The section registry and conversational refinement patterns naturally extend to thesis and IC review later without over-abstracting now.

### Architecture

#### 0. Structured Output is the Foundation

Every LLM call in the memo pipeline returns structured, schema-validated output. This is the single most important implementation decision. Without it, memo quality is unpredictable and downstream consumers (frontend, DB, Ledger) can't trust the shape of the data.

**Why this matters:**
- Consistent section structure across runs (same ticker, different days = same shape)
- Parseable by frontend without regex/heuristics
- Enforceable word count via schema constraints
- Composable — sections can be independently generated and assembled
- Testable — you can validate output shape without reading content

**Implementation:** Use OpenAI structured outputs (response_format with json_schema) or equivalent. Every section generation call returns a typed schema, not freeform markdown. The markdown rendering happens AFTER schema validation, not during LLM generation.

```python
# Section output schema (what the LLM returns)
class SectionOutput(BaseModel):
    """Structured output for a single memo section."""
    title: str
    summary: str              # 1-2 sentence TL;DR
    content: str              # full section content (markdown)
    word_count: int           # actual word count of content
    key_data_points: list[str]  # specific numbers/facts cited
    confidence: Literal["high", "medium", "low"]  # how confident given available data
    data_gaps: list[str]      # what data was missing/thin

# Full memo output schema
class MemoOutput(BaseModel):
    """Structured output for the complete investment memo."""
    ticker: str
    company_name: str
    sections: list[SectionOutput]
    total_word_count: int
    generation_cost_usd: float
    strategy_profile_version: int  # which profile version generated this
```

#### 1. MemoProfile (the core data model)

```python
@dataclass
class MemoSection:
    key: str              # e.g. "opportunity_brief"
    title: str            # e.g. "Opportunity Brief"
    depth: int            # 1-5 (maps to word count targets below)
    focus_directives: list[str]  # what the LLM should emphasize
    base_prompt: str      # the section's base prompt template (from registry)
    data_requirements: list[str] # what data sources this section needs
    enabled: bool         # user can disable sections
    order: int            # display/generation order
    max_tokens: int       # token budget for this section (derived from depth)
    depends_on: list[str] # other section keys whose DATA this section needs

# Depth → concrete targets (calibrated via testing)
DEPTH_SPEC = {
    1: {"words": "100-200",   "max_tokens": 400,  "paragraphs": "1-2", "cost_est": 0.03},
    2: {"words": "200-400",   "max_tokens": 700,  "paragraphs": "2-3", "cost_est": 0.05},
    3: {"words": "400-600",   "max_tokens": 1000, "paragraphs": "3-5", "cost_est": 0.08},
    4: {"words": "600-1000",  "max_tokens": 1600, "paragraphs": "5-8", "cost_est": 0.12},
    5: {"words": "1000-1500", "max_tokens": 2400, "paragraphs": "8-12", "cost_est": 0.15},
}

@dataclass
class RefinementEntry:
    """Typed changelog entry for profile refinements."""
    action: str           # "added" | "removed" | "depth_change" | "focus_change" | "reorder"
    section_key: str | None
    old_value: str | None
    new_value: str | None
    reason: str           # user's words that triggered this
    timestamp: str        # ISO format

@dataclass
class MemoProfile:
    sections: list[MemoSection]
    style_notes: str      # freeform style guidance from conversation
    version: int          # bumps on each refinement
    last_refined: str     # ISO timestamp
    refinement_history: list[RefinementEntry]

    def estimated_cost(self) -> float:
        """Pre-flight cost estimate based on enabled sections and depth."""
        return sum(
            DEPTH_SPEC[s.depth]["cost_est"]
            for s in self.sections if s.enabled
        )

    def exceeds_budget(self, max_cost: float = 2.0) -> bool:
        return self.estimated_cost() > max_cost
```

#### 3. Strategy-to-Profile Mapping

`strategy_to_profile()` is an **LLM call with structured output**. The LLM takes the strategy north_star + dimensions and returns a typed `MemoProfileSchema` that determines which sections are enabled, their depth, and focus directives. This is NOT a rule-based lookup — the LLM interprets the strategy nuance.

```python
# Schema the LLM must return (structured output)
class SectionConfig(BaseModel):
    key: str
    enabled: bool
    depth: int  # 1-5
    focus_directives: list[str]  # 2-5 specific focus areas

class MemoProfileSchema(BaseModel):
    """LLM generates this from strategy context."""
    sections: list[SectionConfig]
    style_notes: str  # overall memo tone/style

# The prompt
STRATEGY_TO_PROFILE_PROMPT = """Given this investor's strategy profile, configure their investment memo.

Strategy: {north_star}
Dimensions: {dimensions}

Available sections (from registry): {registry_keys_with_descriptions}

For each section, decide:
- enabled: should this section be in their default memo?
- depth: 1 (brief, ~150 words) to 5 (deep, ~1200 words)
- focus_directives: 2-5 specific things the LLM should emphasize for THIS investor

Rules:
- Default sections (opportunity_brief, valuation_analysis, financial_quality, risks_bear_case)
  should generally be enabled unless the strategy strongly doesn't need one.
- Add-on sections should be enabled only if the strategy clearly benefits.
- Premium sections should only be included if the data source is available.
- Total enabled sections should be 4-6 to keep cost under $2.
- Depth should vary based on what matters to this strategy. Not everything is depth=3.

Return the MemoProfileSchema."""

async def strategy_to_profile(north_star: str, dimensions: dict,
                               available_data_sources: list[str]) -> MemoProfile:
    """LLM generates a MemoProfile from strategy context."""
    # Filter registry to sections whose data_requirements are met
    available_sections = {
        k: v for k, v in SECTION_REGISTRY.items()
        if all(req in available_data_sources for req in v["data_requirements"])
    }

    result = await llm.generate(
        prompt=STRATEGY_TO_PROFILE_PROMPT.format(
            north_star=north_star,
            dimensions=json.dumps(dimensions),
            registry_keys_with_descriptions=_format_registry(available_sections),
        ),
        response_format=MemoProfileSchema,  # structured output
        reasoning_effort="medium",
    )

    # Hydrate into full MemoProfile with base_prompts from registry
    return _hydrate_profile(result.parsed, available_sections)
```

#### 4. Conversational Refinement

The strategy conversation chat handles refinement via **LLM function calling**. When a user message mentions memo preferences, the AI calls a `mutate_memo_profile` tool.

```python
# Function-calling schema for profile mutations
MEMO_PROFILE_TOOLS = [
    {
        "type": "function",
        "function": {
            "name": "mutate_memo_profile",
            "description": "Update the user's investment memo profile based on their request",
            "parameters": {
                "type": "object",
                "properties": {
                    "mutations": {
                        "type": "array",
                        "items": {
                            "type": "object",
                            "properties": {
                                "action": {
                                    "type": "string",
                                    "enum": ["add_section", "remove_section", "set_depth",
                                             "add_focus", "remove_focus", "set_style", "reorder"]
                                },
                                "section_key": {"type": "string"},
                                "value": {"type": "string"},
                                "reason": {"type": "string"},
                            },
                            "required": ["action", "reason"]
                        }
                    }
                },
                "required": ["mutations"]
            }
        }
    }
]
```

**Routing logic:** The strategy conversation backend already classifies user intent (strategy question vs general chat). Add a third intent: `memo_profile_mutation`. Detection: message mentions "memo", "investment memo", "section", "focus on", "more about", "less about", "add", "remove" in the context of memo output. When detected, include `MEMO_PROFILE_TOOLS` in the LLM call.

**Validation rules:**
- `add_section`: must exist in registry, data_requirements must be met
- `set_depth`: must be 1-5, check if new total cost exceeds $2 budget (warn, don't block)
- `add_focus`: max 8 focus directives per section (prevent directive sprawl)
- `remove_section`: default sections can be disabled but not deleted from profile
- Conflicting directives: LLM is asked to resolve in the mutation call (e.g., "more detail" on a depth=5 section → respond "already at maximum depth")

**Example flow:**

```
User: "For my investment memos, I want more focus on capital allocation history"
→ AI detects memo_profile_mutation intent
→ LLM called with MEMO_PROFILE_TOOLS + current profile + user message
→ LLM returns: mutate_memo_profile({mutations: [
    {action: "add_focus", section_key: "financial_quality",
     value: "capital allocation track record", reason: "user wants capital allocation emphasis"}
  ]})
→ Backend validates: financial_quality exists, enabled, <8 directives ✓
→ Backend applies mutation, bumps version, records RefinementEntry
→ AI responds: "Done — your Financial Quality section will now emphasize capital allocation track record.
   Your memo has 4 sections, estimated cost ~$0.38. Want to see a preview on a specific ticker?"
```

#### 5. Section Interdependencies

Some sections reference data from other sections (e.g., Risks references valuation fair value). The solution: **always run the valuation model internally, regardless of which sections are rendered.**

```python
# In _generate_investment():
# Step 1: Always run valuation model (deterministic, cheap, no LLM)
valuation = await self._run_valuation(ticker, data)

# Step 2: Build shared data context (available to ALL section prompts)
shared_context = {
    "ticker": ticker,
    "company": company_name,
    "price": price,
    "fair_value": valuation["fair_value"],
    "discount_pct": discount,
    "valuation_method": valuation["method"],
    "valuation_assumptions": valuation["assumptions"],
    "market_intel": market_intel,
    "filing_context": filing_context,
    "financials_5yr": financials,
    "sector": sector,
    "sector_key_metrics": sector_profile["key_metrics"],
    "sector_financial_focus": sector_profile["financial_focus"],
    "revenue_cagr_5y": revenue_cagr,
}

# Step 3: Generate only ENABLED sections, in order, with shared context
for section in sorted(profile.enabled_sections(), key=lambda s: s.order):
    prompt = self._build_section_prompt(section, shared_context)
    result = await self.llm.generate(
        prompt=prompt,
        response_format=SectionOutput,  # structured output!
        max_tokens=section.max_tokens,
        reasoning_effort="medium",
    )
```

**Key principle:** The valuation model runs regardless. Section `depends_on` means "this section uses data from that computation," not "that section must be rendered." A user can disable Valuation Analysis (the rendered section) while Risks still gets the fair value number from the model.

#### 6. Prompt Generation

The current `_build_strategy_lens()` gets replaced with `_build_section_prompt()`:

```python
def _build_section_prompt(self, section: MemoSection, context: dict) -> str:
    """Generate a section-specific prompt from MemoProfile + shared context."""

    depth_guide = DEPTH_SPEC[section.depth]

    prompt = f"## {section.title}\n\n"
    prompt += f"Write {depth_guide['words']} words ({depth_guide['paragraphs']} paragraphs).\n"
    prompt += f"Focus on: {', '.join(section.focus_directives)}\n"
    if self.profile.style_notes:
        prompt += f"Style: {self.profile.style_notes}\n"
    prompt += f"\n{section.base_prompt.format(**context)}\n"
    prompt += f"\nReturn your analysis as a SectionOutput with title, summary, content, "
    prompt += f"word_count, key_data_points, confidence, and data_gaps."
    return prompt
```

#### 7. Cold Start & Data Sources

**Cold start:** When a user runs their first memo and has a strategy but no MemoProfile yet, the system calls `strategy_to_profile()` lazily before generation. Flow:

```
User clicks "Generate Memo" for AAPL
→ MemoAgent checks DB for memo_profiles where strategy_id = active strategy
→ No profile found → calls strategy_to_profile(north_star, dimensions, available_sources)
→ LLM returns MemoProfileSchema → hydrated into MemoProfile → saved to DB
→ Memo generation proceeds with the new profile
→ User sees: "I generated your memo profile from your strategy. You can refine it anytime in the strategy chat."
```

**`available_data_sources`:** Derived from user's connector configuration in `workflow.yaml`. At runtime:

```python
def get_available_sources(config: dict) -> list[str]:
    sources = ["sec_10k", "sec_proxy", "yfinance_price", "yfinance_financials"]  # always free
    if config.get("connectors", {}).get("market_data", {}).get("provider"):
        sources.append("fmp_estimates")
        sources.append("fmp_institutional")
    # Future: if config has bloomberg connector, add bloomberg sources
    return sources
```

**`market_intel`:** The output of `fetch_market_intelligence()` (already exists in `backend/memo/market_research.py`). It's a dict with keys like `opportunity_risk`, `competitive_landscape`, `recent_developments`. Generated by GPT-5 mini web search. Passed into section prompts as a formatted string.

**`valuation_model`:** The output of `_run_valuation()` (already exists in MemoAgent). It's a dict with `fair_value`, `method`, `assumptions`, `scenarios`. This is the deterministic valuation computation, not an LLM section.

**`_hydrate_profile()`:** Takes the LLM-generated `MemoProfileSchema` and enriches it with data from the section registry:

```python
def _hydrate_profile(schema: MemoProfileSchema, registry: dict) -> MemoProfile:
    sections = []
    for i, sec_config in enumerate(schema.sections):
        reg_entry = registry.get(sec_config.key)
        if not reg_entry:
            continue  # LLM hallucinated a section key, skip
        sections.append(MemoSection(
            key=sec_config.key,
            title=reg_entry["title"],
            depth=sec_config.depth,
            focus_directives=sec_config.focus_directives,
            base_prompt=reg_entry["base_prompt"],
            data_requirements=reg_entry["data_requirements"],
            enabled=sec_config.enabled,
            order=i,
            max_tokens=DEPTH_SPEC[sec_config.depth]["max_tokens"],
            depends_on=reg_entry.get("depends_on", []),
        ))
    return MemoProfile(
        sections=sections,
        style_notes=schema.style_notes,
        version=1,
        last_refined=datetime.utcnow().isoformat(),
        refinement_history=[],
    )
```

### Settings Philosophy (applies to thesis + IC review later)

This design establishes a pattern that will extend to other agents:

| Agent | Profile Type | Strategy Sets... | User Refines... |
|-------|-------------|------------------|-----------------|
| **Memo** | MemoProfile | Section depths, focus directives, default section set | Add/remove sections, adjust depth, change focus |
| **Thesis** (future) | ThesisProfile | Narrative focus, scorecard dimensions, sector-specific topics | Which dimensions matter most, what "good" looks like |
| **IC Review** (future) | ICProfile | Return hurdles, discount floors, evaluation lens | Threshold values, what the AI reviewer focuses on |
| **Screener** (already built) | ScoringCode | AI-generated Python scoring from strategy | Feedback on results, re-run scoring |

The unified pattern: **Strategy conversation → Agent profile (smart defaults) → Conversational refinement → Persistent profile in DB → Agent reads profile at runtime.**

Each agent's profile is stored in the same table pattern. The strategy conversation is the single entry point for all of them. When a user says "I care more about capital allocation," the AI knows which agents to update and how.

### What This Does NOT Include (Deferred)

- **Usage-based auto-learning** (the "posterior update" from second opinion). The `memo_feedback` table is the schema stub. The auto-learning loop comes later.
- **Unified AgentProfile abstraction** (Approach C). Build MemoProfile first, prove the pattern, then extract the shared layer.
- **Custom prompt editing.** Users don't write prompts. They describe what they want, the AI generates prompts. If we ever add "advanced mode" prompt editing, it's a separate feature.
- **Bloomberg / premium data source integration.** The section registry has `data_requirements` so this is extensible, but we don't build the connectors now.

### Error Handling

Per-section LLM failures should NOT kill the entire memo. The memo ships with N-1 sections and a clear indicator of what failed.

```python
for section in enabled_sections:
    try:
        result = await self.llm.generate(
            prompt=prompt, response_format=SectionOutput,
            max_tokens=section.max_tokens, timeout=60,
        )
        # Validate structured output
        if result.parsed.word_count < DEPTH_SPEC[section.depth]["words"].split("-")[0]:
            log.warning(f"Section {section.key} underweight: {result.parsed.word_count} words")
        section_outputs.append(result.parsed)
    except Exception as e:
        log.error(f"Section {section.key} failed: {e}")
        section_outputs.append(SectionOutput(
            title=section.title,
            summary=f"[Generation failed: {e}]",
            content="",
            word_count=0,
            key_data_points=[],
            confidence="low",
            data_gaps=[f"Section generation failed: {e}"],
        ))
```

**Retry policy:** One retry with `reasoning_effort="low"` if the first attempt fails. If both fail, ship the empty section with the error indicator. The user sees "This section failed to generate" in the UI, not a blank.
